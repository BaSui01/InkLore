# ADR-0003：全栈北京时间契约

- **状态**：Accepted
- **日期**：2026-09-16
- **决策者**：项目负责人
- **关联任务**：INK-031
- **替代关系**：无

## 背景（Context）

创作平台存在大量与"自然日"相关的业务语义：日更统计、连续创作天数、排期计划、写作时长报表、章节发布日期。这类语义的判定必须基于**同一个固定时区**，否则：

- 服务器部署在 UTC 而个人统计按本地时区，会出现"跨天"错位。
- 数据库用无时区 `TIMESTAMP` 存储，跨时区读取会产生不可复现的偏差。
- 不同模块各自调 `time.Now()`，导致同一事件在不同地方属于不同自然日。

项目面向中文网文作者，业务自然日以北京时间为准。

## 决策（Decision）

**存储统一 UTC + 时区信息，业务统一经 `timeutil` 换算北京时间。**

1. 数据库时间列一律使用 `TIMESTAMPTZ`（PG 内部按 UTC 存储）。
2. 业务逻辑、自然日统计、排期计算必须通过 `internal/platform/timeutil` 显式转换为北京时间。
3. 严禁在业务代码中使用系统本地裸时间（`time.Now()` 直接参与业务判定或持久化）。
4. 对外 API 的时间字段使用带时区的 RFC3339 表示。

## 备选方案（Alternatives）

| 方案 | 优点 | 缺点 | 为什么未采用 |
| --- | --- | --- | --- |
| 数据库存本地时间（无时区） | 直观看得懂 | 跨时区不可复现，夏令时/部署迁移即出错 | 无法保证正确性 |
| 全链路 UTC，业务层不转换 | 最简单一致 | "今天写了多少字"按 UTC 判定，与作者直觉不符 | 业务语义错误 |
| 按用户时区各自计算 | 最贴合个体 | 多时区统计不可汇总，实现与测试成本剧增 | 当前用户群集中在同一时区 |

## 后果（Consequences）

**正面**

- 跨时区部署与迁移安全，历史数据不偏差。
- "自然日"在任何模块中定义一致，统计可复现。
- 时间相关 bug 的排查收敛到单一工具包。

**负面 / 代价**

- 每次时间处理都需要显式转换，代码略啰嗦。
- 现有代码存在直接使用 `time.Now()` 的部位（如 `novel/application/service.go`），需要专项清理（INK-031）。

**需要长期承担的义务**

- 新增任何时间列必须 `TIMESTAMPTZ`，任何业务时间判定必须走 `timeutil`。
- 代码评审与护栏脚本需检查裸时间使用。

## 验证方式（Verification）

1. `\d+\s+` 检查迁移文件，确认无 `TIMESTAMP`（无时区）列。
2. 全库检索业务代码中的 `time.Now()`，确认仅出现在允许的边界（如 `timeutil` 内部）或已改造。
3. 构造 UTC 23:30 的时刻，验证自然日统计归属到北京时间的次日。
