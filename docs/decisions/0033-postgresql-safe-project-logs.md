# ADR-0033：安全项目日志的 PostgreSQL 只读检索投影

- **状态**：Proposed（用户已明确要求项目日志入 PostgreSQL；保留期限及故障降级细节待运行验收）
- **日期**：2026-09-28
- **决策者**：项目维护者（按用户本轮需求实施）
- **关联任务**：INK-241
- **替代关系**：无；补充 ADR-0012 的数据库权威原则，不替代安全审计事实表

## 背景（Context）

现有 `slog` 结构日志主要流向标准输出或文件，管理端无法查询历史项目日志；平台审计事件是另一条持久、只追加且租户隔离的安全事实链。用户要求日志存储在 PostgreSQL 并在管理端查询。设计基线要求日志不得包含正文、提示词、凭据、原始请求参数或任意 SQL；Admin operator/auditor 仅读安全投影。若把原始日志整包写数据库，日志反而会扩大敏感数据的留存范围，也可能在数据库失败时递归产生日志。

## 决策（Decision）

1. 在 platform/logger 对已脱敏日志再作严格字段白名单投影，将时间、级别、固定事件名、domain、operation、受控错误码、请求与追踪关联值及有限的安全数字字段写入单独 PostgreSQL 日志表；不存任意原始 `slog` 参数、IP、路径实参或异常文本。
2. 由组合根在数据库迁移验证完成后装配日志持久化；标准输出/文件继续作为数据库不可用时的独立诊断通道。写入失败不得递归记录或影响核心业务事务，页面应真实展示读取失败而不是伪造空日志。
3. 管理端新增只读、安全鉴权且绑定当前租户的分页查询；无跨租户搜索、任意 SQL、日志增删改接口。系统级未带已验证租户上下文的日志单独处理，不能借由任意租户请求泄露其它主体信息。
4. 保留有限保留窗口、查询上限与结构化过滤，不能使项目日志副本绕过审计和内容擦除策略；分页游标绑定当前授权主体与筛选条件。审计日志保持既有 append-only 表与独立 API，不把两类事件混作同一事实。

## 备选方案（Alternatives）

| 方案 | 优点 | 缺点 | 为什么未采用 |
| --- | --- | --- | --- |
| 直接按行读服务器日志文件 | 无新增表与写入成本 | 多实例不一致，历史文件权限和搜索易泄露 | 不满足 PostgreSQL 存储与管理端安全查询需求 |
| 复用平台审计事件表存全部日志 | 只有一套查询 | HTTP/调试日志与不可变审计事实混淆、审计事务语义被破坏 | 审计是业务安全事实，日志是尽力而为的运维投影 |
| 数据库存原始 JSON 日志 | 最容易扩展 | 敏感字段、正文及异常文本可能长久留存 | 违反日志最小化及安全红线 |

## 后果（Consequences）

**正面**：管理员可跨进程查找安全项目日志并通过请求关联定位问题；审计独立只读保持不变。

**负面 / 代价**：数据库增加写负载、迁移、有限保留与查询索引维护；尽力而为的日志写入不保证每条原始流输出都有 PG 副本。

**需要长期承担的义务**：确保过滤字段、租户隔离、循环错误防护和留存清理与新日志字段同步审查；未完成真实 PG 验收时不能声称无丢失或全链路覆盖。

## 验证方式（Verification）

`go build ./...`、`npm run build:admin`、语言服务诊断与项目门禁通过；隔离 PG 验证迁移、分页与筛选、Admin/Creator及跨租户拒绝、敏感输入零落库、PG 写入不可用时业务与输出流仍可用；浏览器验证管理端查询及错误态。不写新的测试文件。
