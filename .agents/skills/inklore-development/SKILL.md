# InkLore 开发交付

## 1. 确认任务与现状

1. 阅读 [AGENTS](../../../AGENTS.md)、用户当前要求和目标目录规则，确认已授权范围。
2. 检查分支、基线、工作区差异及相关 Issue/PR，保留其他人的改动，复用已有任务。
3. 从入口、调用方和数据消费方定位真实实现；[当前架构](../../../docs/architecture.md)提供导航，结论以源码及可复现行为为证据。
4. 按 [资料路由](references/doc-routing.md) 只读本次相关契约与历史理由；历史设计不预设当前功能已完成，也不限制合理演进。

GitHub Issues/Milestones 保存当前任务状态和依赖，PR 保存实现与验收。旧 INK 编号与 backlog 仅供追溯，不要求重新登记同一任务。新建或调整 GitHub 任务按用户授权执行。

## 2. 确定最小改动

- 把验收写成具体操作和可观察结果，覆盖本次变更涉及的失败或权限场景。
- 先查根因和真实调用链，再选择最小有效修复；复用已有组件、错误处理和数据访问方式。
- 按实际职责、依赖和数据 Owner 判断边界，不预设固定领域数量或为单一实现强加接口、工厂、适配层。
- 需要长期保留的取舍，使用 [决策记忆](../inklore-decisions/SKILL.md)；普通局部修复无需先制造 ADR。
- 已有授权覆盖的工作直接推进；真正缺少高风险变更授权或关键决策时，说明证据、影响和具体待决项。

小任务直接完成。只有独立且收益明确的任务才并行派发，给出独占文件和验收范围，公共装配与契约由主代理协调。

## 3. 沿真实链路实施

核对页面或入口 → API/Transport → 应用服务 → 数据或模型调用 → 持久化结果 → 调用方展示。只查看与任务有关的层次，不为符合历史图形创建空层。

- 保留租户/主体权限、事务、版本冲突、幂等、密钥保护和真实外部兼容要求。
- API 字段读取 [机器契约](../../../docs/system-design/api/)，并与实际路由、解码器、前端请求核对；Schema 存在不等于运行时执行了校验。
- 数据演进核对当前迁移与消费方，不改写已经应用的迁移身份和内容。
- 配置追到实际读取者；保存成功不能证明 Worker、模型路由或权限已经使用它。
- Agent 的持久状态、SSE 订阅、取消、审批和产物采纳分别验证；不能用假数据、静默回退或假进度掩盖缺失。
- 前端复用现有共享包与 i18n，保护未保存输入和错误恢复；只改本任务涉及的体验。

## 4. 选择验证

按 [验证矩阵](references/verification.md) 选择相关命令和真实场景。必要时增加能捕获根因的回归测试；纯文案或机械变动不强制新增测试，也不重复全套构建。

执行失败时保留命令、退出码和原始错误，区分已有问题与本次引入的问题。缺数据库、浏览器、模型或其他依赖时写明 `NOT_VERIFIED`，不得将编译通过描述为业务闭环通过。

## 5. 交付与交接

使用 [验收模板](templates/acceptance.md) 或直接在 PR 中写清变更原因、行为、证据和限制。只同步受影响的文档，不在多个文件复制任务状态。

保留确有长期价值的根因、兼容理由或否决方案；按需更新笔记并校验链接。提交、创建 PR、合并与部署分别遵守当前用户授权。

汇报先说结果，再给文件或 PR、验证与剩余阻塞；跨会话交接记录基线、改动、已执行检查和未验证项。
