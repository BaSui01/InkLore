## 1. 结论与证据口径

当前代码有真实的持久化领域服务、租户/owner 校验、修订 CAS、版本快照、事实事件与投影，并不是只有页面原型。但从作者入口到保存、事实确认、完整导出的端到端产品链**尚未闭合**。主要断点集中在组合根未接线、手写 SDK 契约偏离实际 API、编辑器维护两份修订状态，以及界面把空结果/请求失败误解释为业务成功。现有模块化单体和七域足以承载修复，没有证据要求新建编排框架、重复数据平台或微服务。

本文的 `CONFIRMED` 仅表示所描述的**静态实现/接线事实已核到源码**；不能读作真实用户验收通过。`PARTIAL` 表示有实现但跨层接线/用户流程存在确定缺口；`ABSENT` 表示在所查范围内找不到入口或实现；`UNCERTAIN` 表示现有证据不足。所有业务行为的运行栏均为 `NOT_RUNTIME_VERIFIED`。下面的失败结果是从实际调用链得到的可复现预期，尚未通过浏览器/API/数据库实跑。

本子任务只运行过只读源码检索、行号读取和一个 SDK 字面路径比对脚本。脚本在 SDK 的所有 `/v1/...` 路径中找到一个没有任何后端字面注册匹配的路径：`sdk.ts:288 /v1/worldview/novels/:novel_id/revision`。这仍是静态校验，不是 HTTP 运行证据。父任务的 build/CI/隔离迁移证据应另列，不能转化为本报告的产品通过项。

### CR-02 / P1：章节定稿有三处独立断点

1. **查询路径错**：CR-01的 `/revision` 与 `/world-revision` 不一致。`ConfirmChapterModal.tsx:42–52`读取失败后留下error，`:95`在worldRevision为null时禁用按钮。此为当前最先阻断的路径。
2. **保存后确认用旧修订**：`EditorRoute.tsx:343–359`保存成功只更新 `revisionRef/currentRevision`，不更新activeChapter/list metadata。Modal接收 `activeChapter`（`:1053–1056`），提交 `chapter.revision`（Modal`:67–70`）。后端 `confirmation.go:49–50`严格CAS。修复查询路径后，普通“编辑→保存→定稿”仍预期409。UI的已保存禁用保护 `EditorRoute:680–681`不会解决修订来源分叉。
3. **确认后又丢返回修订**：后端 `confirmation.go:63–74`调用saveChapter令revision+1并返回完整chapter；UI `EditorRoute:1058–1062`忽略 `confirmation.chapter`，只将旧activeChapter.status改confirmed，不更新保存revisionRef。其后保存预期409；即使重新加载后保存成功，服务端把章节重置draft（`chapters.go:141`），UI不更新metadata仍可能显示“已定稿”。

**建议**：章节entity/body snapshot保持单一权威状态；加载/保存/确认/冲突解决统一采纳服务端返回chapter。模态框用当前已保存的chapter snapshot并冻结该意图；任何冲突显式刷新/核对，不抹掉CAS。后端CAS是正确保护，不应为迎合UI放宽。

**映射**：#107作者编辑后确认与可重开链；#15 frontend state契约。完整运行证据必须包括save revision2→confirm revision3→再次编辑保存转draft的顺序。

### CR-03 / P1：事实账本存在，但当前“定稿入账”未产生作者事实

`ConfirmChapterModal.tsx:67–70`始终发空 `fact_proposals`；没有事实提取、勾选、冲突解决或checkFacts调用。与此同时`:108–111`承诺本章事实永久入账。Content `confirmation.go:59`只是把提案传给Worldview；`worldview/application/facts.go:97–137`逐提案写事件和heads，空数组不会凭空从正文生成事实。不能把世界修订推进等同事实提取/连续性已完成。

后端有应保留的安全机制：`facts.go:51–52`要求既有事务；`:61–80`检查novel/chapter/version/内容hash；`:82–100`进行world CAS与冲突检查；`:113–119`把源chapter/version/hash写入事件；`:165`以后的retract/supersede通过新事件修订。Content回滚仅回滚正文并转draft，不应删除历史账本；但产品需要明确如何复核旧版来源事实并提交新的提案，否则“回滚后故事事实同步”仍缺流程。

**建议**：把“保存草稿”“确认正文版本”“确认事实提案”语义明确表达，保留作者最后确认。利用现有FactProposal/CheckFacts/CommitFacts、版本hash和事件表闭环，不设第二套事实数据库；没有提案时如实显示本次0条事实。初期可以作者编辑结构化提案，模型提取必须为可审阅建议。

**映射**：#107跨域原子事实确认与人物连续性验收；#15 Owner/事务设计。

### CR-04 / P1：导入导出可达服务缺Files/Reviews接线，却写准备好/成功终态

**真实入口**：`app/domains.go:71`构造Content Options未传Files/Reviews；`:145`把这个实例注册到HTTP。`content/transport/routes.go:113–127`真实调用CreateImport/CreateExport。`content/application/service.go:17–24`构造器不要求Files/Reviews，Options为private字段且全仓无后续setter。平台文件HTTP真实存在并不等于这个服务已经绑定它。

## 5. 应保留的正确机制

1. **数据Owner和统一事务**：Content拥有正文/版本，Worldview拥有事实。`Content.execute`通过既有idempotency事务执行权限与业务（`service.go:115–141`）；正文、历史、scope projection与事件在同一次写中。定稿Facts要求既有UoW，不独立提交。
2. **来源和CAS**：正文和世界修订分别比较；事实事件带章节版本与hash；AI产物UI要求target/revision/原文一致，partial不能采纳。修SDK不能通过取消这些检查“修好前端”。
3. **租户/owner过滤**：Content owner验证creator audience（`service.go:59–90`），仓储`owned`用tenant+novel+实际owner EXISTS（`repository.go:33–38`），写必须Require事务。未证明跨租户漏洞，不应为简化Owner去掉层次。
4. **历史不可变性**：`migrations/r1/000002_content.sql:167–170`版本/writing history触发器，Worldview ledger events+payloads+heads设计。保留原迁移文件、数据库对象与校验和；名称含R1不意味着运行安全机制应删除。
5. **部分成熟前端设施**：书架无限查询及错误快照；共享AuthSession/ApiClient同键401重放、sessionEpoch隔离；编辑器冻结保存意图和显式冲突比较。目标是把同样约束贯穿其他页面，避免再写一套HTTP/恢复/编辑器系统。
