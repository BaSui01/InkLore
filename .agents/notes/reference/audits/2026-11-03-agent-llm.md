# Agent / LLM 真实源码基线审计

基线：`60279c40f5c81982c69d035c0c886931d22334cd`（dev）。范围：只读源码审计；未改业务代码、未访问真实数据库、未调用模型、未运行浏览器。除明确标注外，以下能力均为 `NOT_RUNTIME_VERIFIED`。本报告是临时研究证据，GitHub Issue 的状态不由本报告改变。

## 结论

当前生产装配有真实的 PostgreSQL Run/Node/Job、租约心跳、TAO 循环、模型调用、产物和 SSE 事件实现，不能归为假 Agent。它尚未构成长篇小说创作闭环：持久 Run 的模型输入没有作品正文、大纲、人物与世界观；可执行工具仅 UTC 时间；Workflow 的工具节点和跨节点输入绑定没有完整消费；预算、限流、计费与实际模型调用尚未闭合；通用澄清仅有 DDL/生成契约，应用运行时和界面缺失。

另发现开书问答的确定性事务缺陷：成功回答后，完成幂等命令时没有事务上下文，会返回 `uow: active transaction required`。这与 R1 命名无关，需独立业务修复和隔离 PG 验证，不能混入本次无行为变化的治理清理。

## 3. 可核对的问题与优先级

### A-01：开书回答成功后仍返回错误（P0）

- 源码：`internal/agent/transport/http/novel_guide.go:78–82` 事务只包 BeginCommand；`:99–108` Answer 完成后，用原 request context 调 CompleteCommand。
- `application/novel_creation.go:34–38` 直接委托 repo，没有新建 UoW。
- `infrastructure/novel_creation_repository.go:208,225` 调用 `db(ctx,true)`；该文件 `:26–37` 写入要求 manager.Require；`platform/uow/uow.go:80–84` 无事务返回 ErrTransactionRequired。
- 结果：模型结果和 session 更新可以已提交，但 command 仍 processing；HTTP 返回失败，同键重试只得到版本冲突；FailCommand 的相同错误被 handler 忽略。
- 性质：可由源码确定的事务上下文错误，尚未运行复现。
- 复用：#4、#107。建议用短事务完成/失败命令，明确命令与 session 的原子终态/崩溃协调，再用隔离 PG + 可控模型响应验证成功、重试、断线。

### A-02：续写/改写模型没有收到作品上下文（P0）

- 来源内容在 `domain_services.go:115–125` 被读取，但 `:178–184` 只输出摘要 hash。`PrepareExecution:83–89` 只返回 revision/hash。
- `run_service.go:139–149,224–249` 没有持久化正文/selection/context；创建节点 checkpoint 只保存 user_model（`:251–293`）。
- `scheduler.go:343–356,417–427` 第一轮 ContextText 为空；后续只有工具观察。
- 前端 `AgentWorkbench.tsx:189–197` 发送资源标识、selection 坐标/hash和 instruction，不发送选中文字。后端也未用 selection 读取文本。
- 对作者：请求“续写这一章”“润色选中段落”时，模型只能依据 instruction 和系统提示写文本；没有大纲、人物、世界观、当前章节和选择段。
- 复用：#107，实施应接现有 content 只读 ContextPack/世界观/大纲能力并保留来源 revision/hash及权限，不重新做一套上下文系统。

### A-03：Workflow 可保存，但 tool 节点和数据依赖不能执行（P0）

- `domain/dag.go:50–55` 明确要求 role=tool 有 ToolVersionID 且无 DefinitionVersionID，属于合法 manifest。
- `scheduler.go:252,374–387` 对所有节点调用 executeNodeTAO 并强制 DefinitionVersionID，合法 tool 节点必失败。
- InputBindings 仅在 DAG 校验使用（`dag.go:148–173`）；`run_service.go:266–293` 创建节点时未带绑定；scheduler 不解析上游产物、source_pointer或target_parameter。
- 下游只因依赖成功变 ready（`scheduler.go:758–789`），模型仍收到原 run.Instruction，没有上游输出。
- 对作者：配置“规划→写作→质检”的多步流程可保存，但数据不会传递；纯工具节点不能完成。
- 复用：#15、#107。应先补一个可验证小说流程，按节点类别执行并消费现有 binding，避免新增调度框架。

### A-04：真实工具能力只剩 UTC 时间；审批/MCP 不可达（P1）

- `tool_executor.go:43–58` 唯一 handler 为 platform_utc_now。
- `:84–98` 拒绝 ApprovalRequired/MCPServerID/RemoteToolName/非只读且仅允许该 key。
- `scheduler.go:396–414` 只给模型传 execution_available 的工具，所以 `:582–668` 的审批创建分支在当前生产装配不可达。
- `approval_service.go:238–285` 消费审批后只改 ready、唤醒 job；scheduler重新从 Think开始，不读取已审批 execution 接着 Act。若将来放开工具过滤仍不能据此声称审批闭环。
- 旧 toolkit/MCP/生成工具有源码，但未装配。
- 复用：#106、#107；安全策略应保留，先绑定少量真实只读创作工具，再单独验收审批后的副作用。

### A-05：模型调用绕过现有预算与限流账本（P0/P1，视付费开放范围）

- `domains.go:118–143` 创建 Budget 管理服务，再单独 NewGatewayService(providerRouter)，没有把预算或 admission 注入调用链。
- `gateway_service.go:87–96` 直接 GenerateChat。全仓检索 NewGatewayAdmission/NewRedisAdmission/SetUsageRecorder/SetPool/SetKeyLimiters，除定义外无生产调用。
- `tenant_channel.go:45–60` 排序 LIMIT1；`provider_router.go:529–532` 返回 managed=false 默认值和 leaseID=-1，因此不进入 Pool 计数/熔断。
- `agent_task_model_gateway.go:93–96` 仅赋 token，不赋 CostMicros；`scheduler.go:472–478` SSE 输出0成本却标 estimated=false。
- 对作者/运营：有预算管理页面或账本代码，不能证明调用会受预算限制、真实结算或有全局限流；不能据SSE的0成本判定免费。
- 复用：#103。应把现有预留、租约、调用、结算、失败释放接成唯一调用路径，逐供应商验证真实 usage 与未知结果，避免叠第二账本。

### A-06：通用澄清只到 DDL/契约（P1）

- 已有 `migrations/r1/000011_agent_clarification.sql` 的 agent_run_questions 与事件约束。
- 生成 SDK `agent.gen.ts:560–596` 声明 question GET/answer。
- 但 `transport/http/routes.go:42–58` 没有这两条路由；`domain/run_types.go:11–38` 没有 waiting_clarification；scheduler/event_service、run-ui/Workbench 无 question 事件处理。
- Novel Guide 的 ask_user 是独立会话，不是持久 Run 的通用 Question，不可替代。
- 复用：#104、#106。保留已应用迁移，补真实实现和正反例。

### A-07：开书确认与 session 未绑定，刷新后可能重复创建（P1）

- `AgentNovelGuidePage.tsx:130–142` 使用通用 content_createNovel，请求只有小说字段；随机幂等 key 在 useRef，不跨刷新保存。
- `created_novel_id` 字段存在，repo能更新，但 Go业务中没有赋值/确认处理路由；`routes.go:9–11` 仅start/get/answers。
- 场景：创建请求服务端已成功、客户端未收到响应，刷新页面恢复仍是 proposed session，再次确认生成新key，可创建第二部作品。
- 复用：#4；需要用session确认命令原子绑定创建结果，或证明其他稳定幂等身份可阻断该场景。

### A-08：开书模型调用随HTTP断线取消，processing可能悬挂（P1）

- `novel_guide.go:28,99` 直接用请求 context 调模型；`novel_creation.go:81–101,119–140` 先持久 processing，后同步模型调用。
- 取消后 `fail(ctx,...)` 仍使用已取消 context且其错误被忽略（`:161–168,200–217`），状态可能无法写 failed。
- 重放Start只返回已有session（`:91–100`）；Get只读；前端对processing持续poll（`AgentNovelGuidePage.tsx:90–97`）。
- 未找到 guide 的 Worker恢复/超时修复调度。
- 复用：#4；应接现有持久任务或明确有限故障恢复，不把HTTP重试当重启长任务。

### A-09：SSE 仍不是逐字流；心跳超时触发的abort不会重连（P1）

- 模型端用 GenerateChat（`agent_task_model_gateway.go:88`），整段响应完成后才写 text.delta（`scheduler.go:535–551`）；这是持久事件推送，不是token逐步显示。
- 前端 `stream/client.ts:88–93` 心跳超时调用 abortController.abort；`:224–227` 捕获abort后直接return，没有scheduleReconnect，状态可能停留open。
- `AgentWorkbench.tsx:46–58` Run和游标只在组件内存；未见本界面刷新后用持久run引用自动恢复，仅同页网络恢复。
- 复用：#106、#107；断网、静默连接、刷新、cursor过期需单独真实浏览器验收。

### A-10：长期可靠性边界仍需收敛（P1）

- `run_service.go:25,222,246` 保存30分钟deadline；全仓DeadlineAt/deadline_at搜索只见存取/输出，没有scheduler比较或cancel deadline，不能宣称有硬总时限。
- `scheduler.go:113–124` 租约恢复遇 running 节点会fail execution_outcome_unknown，这是防重复外部副作用的正确保守行为，不应删除。
- `scheduler.go:449–490,622–664` 还有关键event/approval/checkpoint写入忽略错误；当前审批不可达应与未来接线一起修复；usage事件错误已影响可观测性。
- `agent_worker.go:32` 只记录错误类型，不记录安全错误code/runID/trace，使真实失败难定位；不要直接记录原始SQL/key。
- `run_service.go:127–137` count active后创建不见同owner容量锁，需并发验收确认是否其他DB约束保护（未据此断言可突破）。
- 复用：#3、#105、#106。

## 4. 需要保留的有效约束

- Run 绑定 definition/workflow/tool/policy 的不可变版本，是可重放性与安全约束，不属于历史 R1 设计冻结。
- Tenant/Owner 实时资源授权、源码 revision/hash、幂等键、CAS、UoW、租约 epoch/fencing 应保留。
- Artifact只建议、作者显式采纳、事实 Owner写入仍是有效业务机制。
- 外部结果未知时拒绝自动重放是正确风险处理；改进可靠性要先增加可对账证据。
- `migrations/r1/000011_agent_clarification.sql` 和已应用迁移不能改身份、编号、checksum。
- `llm/infrastructure/chat.go:108` 的 `deepseek-r1`、`llm/domain/types.go:360` 的 DeepSeek-R1 是模型名，不是项目阶段污染。
