# ADR-0002：SSE 与 WebSocket 职责隔离

- **状态**：Accepted
- **日期**：2026-09-16
- **决策者**：项目负责人
- **关联任务**：INK-021
- **替代关系**：无

## 背景（Context）

平台存在两类实时需求，特征完全不同：

1. **请求级生成流**：章节正文逐字推送、Agent 思考链（Think Delta）、工具调用回显。特征是请求-响应绑定的长连接、单向、高频率、生命周期随一次生成结束。
2. **系统级广播**：长任务终态、全局状态通知、低频提醒。特征是广播、与具体请求无关、低频、需要双向心跳。

若两者混用同一条通道，会出现：生成流被打断时丢失全局通知；广播连接被生成流占满；协议语义混乱导致前端难以维护。

## 决策（Decision）

**SSE 独占请求级生成流，WebSocket 独占系统级低频广播。**

- AI 文本生成、打字机逐字推流、Think Delta、工具调用回显 → 仅走 HTTP SSE（`text/event-stream`）。
- 长任务终态推送、全局状态通知、低频通知广播 → 仅走 WebSocket。
- 任何"既想流式又想广播"的需求，必须拆成两条通道实现；不允许用 WS 跑生成流，也不允许用 SSE 做广播。

## 备选方案（Alternatives）

| 方案 | 优点 | 缺点 | 为什么未采用 |
| --- | --- | --- | --- |
| 全部用 WebSocket | 一条通道、天生双向 | 与 HTTP 语义脱节，鉴权/中间件/网关兼容成本高；广播与生成互相干扰 | 生成流本质是 HTTP 请求的生命周期延伸 |
| 全部用 SSE | 简单、天然单向流 | 无法服务端主动广播；HTTP/1.1 连接数受限 | 广播场景不适用 |
| 用轮询代替 WS | 实现最简单 | 终态延迟、无谓请求、浪费连接 | 体验与成本都更差 |

## 后果（Consequences）

**正面**

- 生成流可复用既有 HTTP 鉴权、中间件、日志与链路追踪。
- 广播通道连接数少、可长时间保持，不挤占生成连接。
- 前端可分别处理两类事件，错误隔离清晰。

**负面 / 代价**

- 前端需要维护两套长连接客户端。
- 需要明确约定两类事件的命名空间，否则仍会混淆。
- 若未来出现反向（客户端→服务端）的生成控制需求，SSE 需要额外 HTTP 端点配合。

**需要长期承担的义务**

- WS 服务端在 M6（INK-021）落地，落地前不得把广播需求塞进 SSE。

## 验证方式（Verification）

1. 生成相关端点响应头为 `text/event-stream`。
2. WS 端点仅订阅终态/通知类事件，不含任何 token 级流。
3. 断流测试：生成流中途中止时，WS 广播通道不受影响且全局通知仍可达。
