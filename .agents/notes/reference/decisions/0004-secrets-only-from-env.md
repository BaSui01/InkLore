# ADR-0004：Provider 密钥只从环境变量或 Secret Store 注入

- **状态**：Accepted
- **日期**：2026-09-16
- **决策者**：项目负责人
- **关联任务**：INK-019
- **替代关系**：无

## 背景（Context）

平台需要接入多家模型供应商（OpenAI、DeepSeek、Anthropic、Gemini、Ollama 等），每个 Provider 可能配置多个 Key（轮换池）。同时系统已具备 Provider/渠道管理接口，容易顺理成章地把密钥当作普通字段入库并由前端回显。

风险：数据库泄露即全部密钥泄露；日志方便排查会把 Key 打进去；前端返回密钥会留在浏览器与代理日志中。这些后果都不可逆。

## 决策（Decision）

**密钥的写入与读取都只经过环境变量或 Secret Store，系统内部只持有脱敏元数据。**

1. 所有 Provider API Key 仅允许通过环境变量（如 `OPENAI_API_KEY`、`DEEPSEEK_API_KEY`）或 Secret Store 注入。
2. 严禁明文入库、严禁打印到任何日志、严禁返回给前端响应。
3. 数据库仅保存脱敏元数据（如 `sk-****abcd`、Key 别名、状态、权重、配额）。
4. 密钥只在发起上游请求的瞬间读取，不进入任何可序列化的结构体。
5. 管理接口对密钥字段一律返回脱敏值，写入操作仅接受"引用名"而非明文。

## 备选方案（Alternatives）

| 方案 | 优点 | 缺点 | 为什么未采用 |
| --- | --- | --- | --- |
| 加密入库（应用层对称加密） | 管理界面可自助配置 | 密钥与密文同库，解密密钥泄露即全泄露；轮换困难 | 安全边界没有实质提升 |
| 明文入库 | 最简单 | 一次数据库泄露即全量泄露 | 不可接受 |
| 只支持环境变量，不支持 Secret Store | 实现最少 | 生产环境密钥轮换与审计困难 | 覆盖不全 |

## 后果（Consequences）

**正面**

- 数据库转储、日志归档、前端响应三条泄露路径被同时切断。
- Key 轮换不需要改数据库，只需更新环境或 Secret Store 并重启/热加载。
- 符合合规审计对密钥管理的基本要求。

**负面 / 代价**

- 运维需要维护环境变量或 Secret Store，不能纯靠界面完成配置。
- 多租户/多用户场景下，用户自带 Key 的诉求无法用当前方案直接满足，需要未来单独设计（届时必须新增 ADR）。
- 本地开发需要 `.env`，且必须确保 `.env` 不进版本库。

## 需要长期承担的义务

- 新增任何与模型 Provider 交互的入口，都必须遵守同一注入方式。
- 日志脱敏（`platform/logger/sanitizer.go`）需覆盖新增字段。
- `.env` 必须在 `.gitignore` 中（M0 已完成项）。

## 验证方式（Verification）

1. 全库检索：不存在把 Key 作为结构体字段序列化返回的路径。
2. 管理接口返回的 Provider 详情中，密钥字段为脱敏值。
3. 在配置了 Key 的环境下抓取日志，全文检索 Key 原文，零命中。
