# 0013 · 任务级模型策略与模型解析顺序

- 状态：Accepted
- 日期：2026-09-17
- 关联：INK-066、INK-065、INK-072、ADR-0005

## 背景

模型选择此前只有两个入口：**调用方在请求体里写 `model`**，或**部署侧在环境变量里写**（`SUMMARY_MODEL`、`WRITING_TOOL_MODEL`、`EMBEDDING_MODEL`）。这带来三个具体问题：

1. **粒度错**：一个 `SUMMARY_MODEL` 同时决定了所有摘要任务的模型，但"章节摘要"和"命名生成"对成本与质量的要求完全不同（前者要便宜快，后者要敢发散）。
2. **改不动**：调整模型要改环境变量并重启进程，作者/运营在界面上无处可调。
3. **不可观测**：``llm_usage_records`` 只能按模型与渠道聚合，答不出"这个月大纲生成花了多少"。

同时 INK-072 引入的 6 个写作工具**必须**依赖模型，如果每个工具各自读一个环境变量，就会出现 6 个各写各的默认值、彼此不一致的局面。

## 决策

### 1. 引入"创作任务"作为模型选择的第一类维度

固定 7 个任务标识（`outline` / `draft` / `review` / `summary` / `naming` / `deai` / `embedding`），落表 `llm_task_policies`，键为 `(tenant_id, task_key)`。

任务标识是**产品语言**而不是代码路径：新增一个任务需要显式登记，避免"随手加一个字符串当任务名"导致统计口径发散。

### 2. 模型解析顺序是全局契约，必须唯一

任何一次模型调用，模型名的确定顺序恒为：

```text
调用方显式指定的 model  >  任务级策略（llm_task_policies）  >  部署侧环境变量默认值
```

- 三挡都缺席时**明确报错**，不静默挑一个模型（延续 ADR-0005）。
- 策略 `enabled=false` 与"策略不存在"语义相同，都表示"回到下一挡"；运营只要关开关就能回退，不必删记录。
- 参数（温度 / max_tokens / 超时 / 重试）遵循同一顺序；工具代码里的温度降级为 `DefaultTemperature`，即"既没有显式值也没有策略时才生效的建议值"。

### 3. 参数必须在调用侧落地，不允许只入库

策略里声明的 `timeout_seconds` / `max_retries` / `max_tokens` 必须在真实调用路径上生效（超时用 context 控制、重试用有上限的循环、max_tokens 透传到上游请求体）。**只存不用的配置字段视为缺陷**——那正是 AGENTS.md §5.5 记录的"配置声明无实现"。

### 4. 用量按任务维度留痕

`llm_usage_records.task_key` 记录本次调用属于哪个任务，失败调用同样记录（`status=failed`）。任务策略不改变用量审计的既有语义，只是多一个聚合维度。

### 5. 策略解析跨域但归属 llm 域

任务策略属于**模型基座域**（llm），不属于任何调用方。消费方（作品域的摘要端口、Agent 工具域的生成端口）只依赖一个只有一个方法的小接口 `ResolvePolicy`，由 `internal/app/adapters` 装配——不把 llm 域的服务类型泄露到消费方，符合 AGENTS.md §1.2 的跨域红线。

## 备选方案与后果

- **备选：把模型写在调用方代码或每域配置里** —— 拒绝。会让同一件事（"摘要用哪个模型"）在多个地方有多个答案，且无法按任务统计成本。
- **备选：策略只作为"建议"，调用方可随意忽略** —— 拒绝。这样"运营改了控制台但没生效"会成为常态；因此把解析顺序写成契约，并在适配器里集中实现。
- **后果：多了一次数据库查询**。适配器每次生成前解析一次策略。这是可接受的：模型调用本身是毫秒的数十倍量级，且策略表按 `(tenant_id, task_key)` 有唯一索引。
- **后果：任务标识成为需要维护的产品面**。新增任务时必须同时登记标识与默认语义，否则任务策略覆盖不到；这是有意的摩擦。
